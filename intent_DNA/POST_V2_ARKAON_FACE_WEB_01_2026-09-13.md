## Locked intent

This is not merely a one-character production task. It is the Post-V2 reference project in which the relevant ARKAON planning, architecture, governance, building, verification, change-analysis, supervision, evidence, recovery, and reporting capabilities are developed and exercised across the full 3D face workflow.

All actions follow:

`READ → ANALYZE → PROPOSE → AUTHORIZE → EXECUTE → VERIFY → REPORT`

Proposal is not execution. Purchases, external uploads, regeneration, asset mutation, publication, and deployment require the applicable explicit human authorization.

## Locked workflow

1. `IDENTITY-01` — generate and approve a same-identity multi-view A-pose/face reference package and lock its evidence.
2. `MESHY-01` — acquire a private model/base rig and qualify topology, rig, skin, rights, privacy, and provenance.
3. `FACE-01` — consume sealed V2 read-only and produce only an isolated Post-V2 derived face candidate.
4. `QA-01` — verify facial behavior and classify `PASS / REPAIR / REGENERATE / REJECT`.
5. `REPAIR-01` — repair the smallest evidenced failed region; whole-face regeneration requires separate human authorization.
6. `WEB-01` — stage, reload, optimize, and package the QA-PASS candidate for the ARKAON web runtime.

## Locked boundaries

- Do not reopen or rewrite V2 CR01–CR04, IRG, canonical semantics, receipts, or digests.
- Do not publish user/Meshy source binaries, derived character binaries, private reference images, visual receipts, credentials, or identifying prompts/seeds.
- Do not infer facial-rig readiness from a marketplace/provider label.
- Do not invent universal identity, topology, geometry, or web-performance thresholds; calibrate and lock them from rights-confirmed private evidence.
- Do not overwrite a previous PASS artifact. Stage uniquely, verify, then publish atomically only after separate authorization.
- Default repair-cycle maximum is three. Further cycles require explicit human approval.

## Acceptance lock

The machine-readable R1 spec defines AC-01 through AC-16 and all required gates. Product PASS requires, at minimum, governance, V2 immutability, identity, input qualification, actual face deformation, expression distinction, eye/mouth integrity, neutral return, body/skin preservation, change analysis, GLB reload, web runtime, privacy/license, evidence-chain, fail-closed, and Human Final PASS.

Known minimum facial runtime evidence includes `Blink_L`, `Blink_R`, `Jaw_Mouth`, `VISEME_AA`, `VISEME_OH`, `VISEME_EE`, a talking clip, `sourceUnmutated=true`, and `bodySkinDigestMatch=true`.
